3. Identified the authenticated proxy parsing problem

Initially, the proxy environment contained credentials:

https_proxy=http://nishu:PROXY_PASSWORD@10.31.212.14:8085


OpenFortiVPN parsed this incorrectly:

proxy_host: nishu
proxy_port: PROXY_PASSWORD@10.31.212.14:8085


This caused:

getaddrinfo: Temporary failure in name resolution


To avoid the parsing problem, OpenFortiVPN was configured with a proxy URL containing only the proxy host and port:

https_proxy=http://10.31.212.14:8085
HTTPS_PROXY=http://10.31.212.14:8085

4. Changes made on the Squid proxy server

Squid configuration file:

/etc/squid/squid.conf


The following ACLs were added:

acl openfortivpn_client src 10.31.0.87/32
acl fortigate_sslvpn dst 182.19.54.189/32
acl fortigate_sslvpn_port port 4433
acl CONNECT method CONNECT


Port 4433 was added to the permitted SSL ports:

acl SSL_ports port 443
acl SSL_ports port 4433


The narrow no-auth rule was added:

http_access allow openfortivpn_client fortigate_sslvpn fortigate_sslvpn_port CONNECT


This rule allows proxy authentication bypass only when all four conditions match:

Source IP:       10.31.0.87
Destination IP:  182.19.54.189
Destination port: 4433
HTTP method:     CONNECT


The normal authenticated proxy rule remains:

http_access allow allowed_ips authenticated


The final deny rule remains:

http_access deny all

Correct rule order

The relevant Squid section should be ordered like this:

acl authenticated proxy_auth REQUIRED

acl allowed_ips src 10.31.0.140
acl allowed_ips src 10.31.0.87
acl allowed_ips src 10.31.1.124
acl allowed_ips src 10.31.1.183

acl openfortivpn_client src 10.31.0.87/32
acl fortigate_sslvpn dst 182.19.54.189/32
acl fortigate_sslvpn_port port 4433

acl SSL_ports port 443
acl SSL_ports port 4433

acl Safe_ports port 80
acl Safe_ports port 443
acl Safe_ports port 1025-65535

acl CONNECT method CONNECT

http_access deny !Safe_ports
http_access deny CONNECT !SSL_ports

# Restricted OpenFortiVPN exception
http_access allow openfortivpn_client fortigate_sslvpn fortigate_sslvpn_port CONNECT

# Normal authenticated users
http_access allow allowed_ips authenticated

http_access deny all


The exception was placed before the authenticated-user rule so OpenFortiVPN does not receive a proxy authentication challenge.

6. Removed incorrect routing and DNAT workarounds

During troubleshooting, a route had been added:

182.19.54.189 via 10.31.212.14


This attempted to use the Squid server as a Layer 3 gateway. That is not required for HTTP CONNECT proxying.

The route was removed:

sudo ip route del 182.19.54.189 via 10.31.212.14 dev enp5s0


Routing was checked:

ip route get 182.19.54.189


A DNAT rule had also been tested:

182.19.54.189:4433 -> 10.31.212.14:8085


This caused TLS errors because raw SSL VPN traffic was sent directly to Squid's HTTP proxy port.

NAT rules were inspected:

sudo iptables -t nat -L OUTPUT --line-numbers -n


The test DNAT rule was removed using its displayed line number:

sudo iptables -t nat -D OUTPUT RULE_NUMBER


The final working setup does not use client-side DNAT or a manual route to Squid.

12. Fixed systemd authentication failure

The first systemd start showed:

Connected to gateway.
Could not authenticate to gateway.


This happened because systemd does not have an interactive terminal and could not answer the VPN password prompt.

For unattended service operation, this line was required in the root-only configuration:

password = YOUR_VPN_PASSWORD
