You want two related but separate things: central management of prox22, prox23, and prox24, plus automatic VM recovery if one node fails. The safest design using your requested ZFS is a 3-node Proxmox cluster + identical local ZFS pools + scheduled ZFS replication + Proxmox HA, but understand that local ZFS replication is not the same as fully shared storage.

Proxmox clustering is multi-master, so after clustering, any node’s Web UI can manage all three nodes. You do not install a separate management server.

How each component works
Proxmox cluster
Joins the three servers into one management interface.
Synchronizes Proxmox configuration through pmxcfs and Corosync.
Any cluster node can manage the complete cluster.
It does not automatically copy VM disks by itself.
ZFS
Provides local redundant storage on each physical server.
Each node needs its own direct-attached disks.
Do not put ZFS disks behind hardware RAID.
Prefer enterprise SSDs with power-loss protection.
Proxmox recommends additional memory for ZFS, approximately 1 GB for each TB of used storage.
ZFS replication
Periodically copies a VM’s ZFS volumes from its current node to another node.
This makes HA with local storage possible, but the copy is asynchronous.
A sudden failure can lose changes made since the most recent successful replication.
HA Manager
Monitors only the VMs and containers explicitly added as HA resources.
If a node fails, HA can restart those resources on another available node.
HA Manager provides automatic fault detection and failover.
Important decision: ZFS replication or Ceph?

For your current plan, use ZFS replication if:

Each node has local disks.
You want an easier design than Ceph.
A small replication recovery point is acceptable.
Your network is not suitable for heavy distributed-storage traffic.

Consider Ceph instead of ZFS replication when you require distributed redundant VM storage across all three hosts. Proxmox supports distributed storage such as Ceph RBD and recommends redundant multi-gigabit networking depending on the storage design.

My recommendation for you is:

Build the Proxmox cluster first.
Create identical ZFS pools on all nodes.
Test manual migration.
Configure ZFS replication.
Add only one noncritical test VM to HA.
Perform controlled failure testing.
Add production VMs gradually.

Do not configure HA before storage and replication are proven.

Phase 4: Identify disks for ZFS

This step is potentially destructive. Creating a ZFS pool erases the selected disks.

On each node run:

lsblk -e7 -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL,SERIAL


Also:

findmnt
pvs
vgs
lvs
zpool status


Check disks by stable ID:

ls -l /dev/disk/by-id/


Never create pools using guessed names such as /dev/sdb. Use /dev/disk/by-id/... because /dev/sdX names can change.

Do not select these
Proxmox OS disk
/boot or EFI disk
Existing LVM physical volume
Disk containing local-lvm
Mounted filesystem
Disk holding backups
Hardware RAID logical disk intended for another purpose

Before creating anything, verify selected disks have no mounted data:

lsblk -f /dev/disk/by-id/SELECTED-DISK
wipefs -n /dev/disk/by-id/SELECTED-DISK


wipefs -n inspects signatures without erasing them.

Phase 5: Choose the correct ZFS layout

Use the same pool name on all nodes, for example:

tank


Recommended general layouts:

Two disks per node: ZFS mirror
Four disks per node: two mirrored vdevs
Six or more disks: mirrors for VM performance, or RAIDZ depending on capacity requirements

For VM workloads, mirrored vdevs are generally the simpler performance-oriented strategy.

Do not combine ZFS with a hardware RAID layer. Proxmox explicitly states that ZFS and Ceph are not compatible with hardware RAID controllers.

Example only: two-disk mirror

Replace both device IDs with the actual disks on that particular node:

zpool create \
-o ashift=12 \
-f tank mirror \
/dev/disk/by-id/DISK-A \
/dev/disk/by-id/DISK-B


The -f option can overwrite existing signatures. Use it only after confirming the correct disks with lsblk and wipefs -n.

Verify:

zpool status
zpool list
zfs list


Enable regular trimming for SSDs:

zpool set autotrim=on tank
zpool get autotrim tank


Repeat with each node’s own physical disks, but preserve the same pool name tank.

Phase 8: Configure ZFS replication

In the GUI:

Select test VM
  → Replication
  → Add


Configure:

Target: another node
Schedule: based on your recovery-point requirement
Rate limit: set if replication could saturate the network


CLI format:

pvesr create VMID-0 \
--target prox23 \
--schedule '*/15'


Check jobs:

pvesr list
pvesr status


After a scheduled execution, verify the target pool:

zfs list -r tank


Start with one target. Do not create overlapping or excessive replication jobs before measuring network and storage load.

Remember: replication is periodic, not synchronous. A host failure can lose changes newer than the last completed replication.

Phase 9: Prepare HA safely

The HA stack is built into Proxmox. HA Manager monitors selected resources and can handle failover, relocation, migration, start, and stop operations.

Verify services on every node:

systemctl is-active pve-ha-lrm
systemctl is-active pve-ha-crm
systemctl is-active corosync


Verify quorum:

pvecm status


Do not enable HA unless all three nodes:

Are online
Show stable quorum
Have matching zfs-vm storage
Have successful replication
Have compatible CPU/network/bridge configuration
Can start the test VM
Network bridge consistency

The VM bridge name must exist on every target node.

Check:

grep -nE '^auto |^iface |bridge-' /etc/network/interfaces


For example, if the VM uses vmbr0, then vmbr0 must be valid on every node where HA may start it.

Backup is still mandatory

HA and ZFS replication are not backups:

HA can replicate accidental deletion or corruption.
Replication does not provide independent long-term restore points.
A cluster configuration error can affect all nodes.

Use separate Proxmox Backup Server or independent backup storage. Proxmox includes backup and restore as a separate feature area from HA and storage replication.
