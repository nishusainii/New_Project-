1. Overview & Architectural Role of NFS in Proxmox VE

Network File System (NFS) provides a standardized, shared, file-level storage backend across all nodes in a Proxmox VE cluster. While block-level Ceph RBD and local ZFS are ideal for active virtual machine execution, NFS serves as the optimal centralized repository for multi-node operations:

Centralized Backups (VZDump)
• All 3 to 5 cluster nodes write automated VM/LXC backup archives (.vma.zst) to a unified NFS target.
• Centralized prune and retention policies across the entire datacenter.
Shared ISO & Templates
• Download an ISO or CT template once; instantly available across all cluster nodes.
• Eliminates redundant storage consumption across individual hypervisor hosts.
Shared VM Disks & Snippets
• Supports QCOW2/RAW VM disk images.
• Supports zero-copy live VM migration without SAN storage.
• Stores shared Cloud-Init YAML configuration snippets.

2. Supported PVE Content Types on NFS

Proxmox VE automatically creates structured subdirectories inside the NFS export path based on configured content flags:

Content Flag Subdirectory Path on NFS Typical File Format Primary Use Case in Production
backup <export>/dump/ vzdump-qemu-*.vma.zst Automated scheduled VZDump guest backups
iso <export>/template/iso/ *.iso (e.g. Ubuntu, Windows) Guest operating system installation media
vztmpl <export>/template/cache/ *.tar.zst, *.tar.gz LXC container base OS templates
images <export>/images/<VMID>/ vm-<VMID>-disk-*.qcow2 Virtual machine virtual disk images
rootdir <export>/subvol/<CTID>/ Subvolumes / raw container root Container root filesystems
snippets <export>/snippets/ *.yaml, *.yml, *.sh Cloud-init user-data, vendor-data, and hook scripts

3. Network Fabric & 10G Subnet Routing

To achieve line-rate backup transfer speeds (> 600 MB/s) and eliminate network contention on Corosync cluster heartbeats, NFS traffic must be routed strictly across the dedicated 10G/25G optical network interface (nic3):

Subsystem Network Interface Subnet Range MTU Setting Design Consideration
Management & Corosync vmbr0 (eno1 - 1G) 10.31.6.0/22 1500 (Standard) Dedicated to cluster quorum; zero storage traffic
NFS Storage & Migration nic3 (Broadcom 10G) 192.168.10.0/24 9000 (Jumbo) Dedicated 10Gbps optical fabric for Ceph and NFS
IP ADDRESSING BEST PRACTICE: Always specify the NFS Server's 192.168.10.x IP address (never the management 10.31.6.x address) when mounting NFS in Proxmox. This forces all streaming I/O through the 10GbE optical link.

4. Phase 1: 10-Disk Storage Pool Architecture & Provisioning

Before initializing the NFS daemon, the 10 physical disks must be aggregated into an enterprise-grade resilient volume. The optimal storage layout depends directly on the intended I/O pattern:

4.1. Storage Topology Comparison for 10 Disks

Topology Usable Space (10x 2TB drives) Fault Tolerance Read/Write Profile Production Recommendation
ZFS RAIDZ2 (Single 10-Disk vdev) ~80% (8 Data + 2 Parity) ~16 TB Survives any 2 disk failures High sequential throughput; moderate random IOPS Recommended for VZDump Backups, ISOs & Templates
ZFS Striped Mirrors (RAID 10: 5 pairs) 50% (5 Data + 5 Mirror) ~10 TB Survives 1 disk per pair (up to 5 total) Maximum random IOPS; fastest rebuild times Recommended for Active VM Disks (QCOW2/RAW)
ZFS Dual RAIDZ2 (2x 5-disk vdevs) 60% (6 Data + 4 Parity) ~12 TB Survives 2 disks per vdev (up to 4 total) Balanced random IOPS and sequential throughput Mixed workloads (VM disks + VZDump backups)
Linux Software RAID 6 (`mdadm` + XFS) ~80% (8 Data + 2 Parity) ~16 TB Survives any 2 disk failures High sequential throughput; standard POSIX filesystem Non-ZFS environments or systems with low RAM

4.2. Disk Discovery & Persistent Identifier Mapping

Identify disks using persistent serial or WWN paths rather than ephemeral device letters (/dev/sdX):

4.4. ZFS Dataset Creation & Recordsize Tuning

Set dataset record sizes matching your target workload to maximize disk efficiency and minimize fragmentation:

Shell Commands: Create & Tune ZFS DatasetStorage Host
# Create dedicated dataset with zstd compression and atime disabled
$ zfs create -o compression=zstd -o atime=off nfs-pool/pve-storage
# For VZDump backups and ISOs, set recordsize to 1M (drastically improves throughput)
$ zfs set recordsize=1M nfs-pool/pve-storage
# Verify dataset properties
$ zfs get compression,recordsize,mountpoint nfs-pool/pve-storage
NOTE ON HARDWARE RAID CONTROLLERS: If using a hardware RAID controller (e.g. Dell PERC / MegaRAID), configure a 10-disk RAID-6 virtual disk with 1MB stripe size and Write-Back cache enabled, then format with XFS using mkfs.xfs -K /dev/sdX.

5. Phase 2: Deploying & Configuring the NFS Server Daemon

Configure the Linux NFS Kernel Server on the host managing the 10-disk array (e.g. dedicated NAS or designated cluster host):

5.1. Install Packages & Set Storage Permissions

Shell Commands: Install NFS Packages & Configure DirectoryNFS Host
# 1. Install kernel NFS server and RPC packages
$ apt update && apt install -y nfs-kernel-server rpcbind
# 2. Configure POSIX permissions for nobody:nogroup
$ chown -R nobody:nogroup /nfs-pool/pve-storage
$ chmod 777 /nfs-pool/pve-storage

5.2. Multi-Thread NFS Daemon Tuning for 10 Disks

By default, Linux runs only 8 worker threads for NFS. A 10-disk storage array handling concurrent multi-node backup streams can saturate 8 threads, causing I/O queuing. Increase worker threads to 32 or 64:

File Configuration: /etc/nfs.conf (or /etc/default/nfs-kernel-server)NFS Host
# Configure 32 parallel worker threads
[nfsd] threads=32
# Apply thread update:
$ systemctl restart nfs-kernel-server

5.3. Configure `/etc/exports` for Proxmox 10G Subnet

Edit /etc/exports to restrict access exclusively to the Proxmox 10G network fabric (192.168.10.0/24):

File Configuration: /etc/exportsNFS Server
# Proxmox VE Cluster 10G Optical Fabric Export
/nfs-pool/pve-storage 192.168.10.0/24(rw,sync,no_subtree_check,no_root_squash,no_all_squash,sec=sys)
# Reload export configuration live without restarting service:
$ exportfs -arv
exporting 192.168.10.0/24:/nfs-pool/pve-storage
$ systemctl enable --now nfs-kernel-server rpcbind

Understanding Export Parameters

Option Parameter Recommended Setting Engineering Rationale
rw Read-Write Mandatory for creating backup archives, uploading ISOs, and writing VM images.
sync Synchronous writes Guarantees write integrity to disk before acknowledging I/O. Prevents corrupted backup chunks.
no_subtree_check Disabled check Enhances transfer speed and prevents file transfer aborts when renaming backup files.
no_root_squash Allow Root Access CRITICAL: Proxmox backup processes run as root. Without this, PVE cannot create backup archives or write image metadata.
sec=sys Standard UNIX Auth Standard UID/GID matching for secure, fast internal cluster access over private VLANs.

5.4. Firewall Configuration (Port 2049 & 111)

Shell Commands: Open NFS Firewall Ports on UFW / IPTablesNFS Server
# Allow NFS v4 (TCP 2049) and RPC (TCP/UDP 111) from 10G subnet only
$ ufw allow from 192.168.10.0/24 to any port 2049 proto tcp
$ ufw allow from 192.168.10.0/24 to any port 111 proto tcp
$ ufw allow from 192.168.10.0/24 to any port 111 proto udp

6. Phase 3: Mounting NFS Storage in Proxmox VE

Step 6.1: Verify Remote NFS Reachability from Proxmox Nodes

Shell Command: Query NFS Exports from PVE NodeTarget: prox22

Step 6.2: Method 1 — Adding NFS via Proxmox CLI (`pvesm`)

Adding NFS storage via pvesm add nfs automatically propagates cluster-wide to all nodes via /etc/pve/storage.cfg:

Shell Command: Add NFS Storage via PVE Storage ManagerTarget: prox22
$ pvesm add nfs nfs-10disk-storage \ --server 192.168.10.50 \ --export /nfs-pool/pve-storage \ --content backup,iso,vztmpl,images \ --options "vers=4.2,tcp,nconnect=8,timeo=600,retrans=2" \ --prune-backups "keep-last=3,keep-daily=7,keep-weekly=4,keep-monthly=12"
# Verify storage status across all cluster nodes:
$ pvesm status

Step 6.3: Method 2 — Adding NFS via Proxmox Web GUI

  1. Log in to the Proxmox Web GUI (https://10.31.6.172:8006).
  2. In the left navigation tree, select Datacenter ➔ Storage ➔ Click Add ➔ Select NFS.
  3. Enter parameters:
    • ID: nfs-10disk-storage
    • Server: 192.168.10.50 (NFS Server 10G Optical IP)
    • Export: Select /nfs-pool/pve-storage from dropdown
    • Content: Select VZDump backup file, ISO image, Container template, Disk image
    • Nodes: Leave empty (All nodes) for cluster-wide mount
  4. Click Add. Proxmox synchronously mounts the NFS volume across all nodes within seconds.

7. Phase 4: 10GbE High-Performance Tuning Parameters

Default Linux NFS uses a single TCP stream. On high-speed 10GbE optical interconnects, configure connection multiplexing (nconnect=8) and 1MB buffers:

Mount Option Recommended Value Performance Benefit on 10G Optical Interconnect
vers=4.2 NFSv4.2 Enables Server-Side Copy (SSC) and sparse file allocation for ultra-fast VM cloning.
nconnect=8 8 TCP Streams Multiplexes RPC requests across 8 parallel TCP connections, saturating 10GbE bandwidth.
rsize=1048576 1 MB Read Buffer Optimizes sequential restore throughput from NFS to local Ceph/ZFS pools.
wsize=1048576 1 MB Write Buffer Optimizes VZDump streaming backup throughput (> 600 MB/s sustained).
timeo=600 60 Seconds Timeout Prevents premature timeout during high-throughput parallel backup commits.

8. Phase 5: Automated Scheduled Backups (VZDump) to NFS

Step 8.1: Schedule Daily Backups via Proxmox Datacenter

  1. In PVE GUI: Datacenter ➔ Backup ➔ Click Add.
  2. Configure parameters:
    • Node: All (Entire Cluster) | Storage: nfs-10disk-storage
    • Schedule: 01:00 (Nightly at 1:00 AM) | Selection Mode: All guests
    • Mode: Snapshot (Zero downtime) | Compression: Zstandard (zstd)
    • Retention/Prune: Keep last 3, Keep daily 7, Keep weekly 4, Keep monthly 12
  3. Click Create. Automatically registered in /etc/pve/vzdump.cron.

9. Phase 6: Maintenance & Troubleshooting Playbooks

9.1. 10-Disk Pool Maintenance & Disk Replacement

Playbook: Monitor Health, Scrub & Replace Failed DiskStorage Host
# 1. Check array status and error counters
$ zpool status nfs-pool
# 2. Initiate monthly background data scrub
$ zpool scrub nfs-pool
# 3. Disk Replacement Procedure:
$ zpool offline nfs-pool /dev/disk/by-id/old-drive-serial
# (Physically swap drive in chassis hot-swap bay)
$ zpool replace nfs-pool /dev/disk/by-id/old-drive-serial /dev/disk/by-id/new-drive-serial

9.2. Playbook A: NFS Storage Shows Question Mark `(?)` Icon in Web GUI

Playbook: Diagnose and Re-arm Inactive NFS StorageCluster Terminal
# 1. Test basic IP and port connectivity over 10G optical interface
$ ping -c 3 192.168.10.50 && nc -zv 192.168.10.50 2049
# 2. Check if export is broadcasted
$ showmount -e 192.168.10.50
# 3. Trigger manual storage scan and mount refresh
$ pvesm set nfs-10disk-storage --disable 1 && sleep 2 && pvesm set nfs-10disk-storage --disable 0
$ pvesm status

9.3. Playbook B: Stale File Handle (`ESTALE`) Resolution

Playbook: Clear Stale Mountpoints via Lazy UnmountTarget Node
# 1. Force detach stale mount from namespace
$ umount -l /mnt/pve/nfs-10disk-storage
# 2. Refresh storage status to trigger clean reconnection
$ pvesm status

9.4. Playbook C: Node Boot Hangs Waiting for Unreachable NFS Server

If the NFS server is powered down, Proxmox nodes take up to 90 seconds per mount to boot due to blocking systemd mount units. Enable non-blocking systemd automounting:

Playbook: Enable Non-Blocking Auto-Mounting (x-systemd.automount)Target Node
# Update PVE storage options to include nofail and background automounting:
$ pvesm set nfs-10disk-storage --options "vers=4.2,tcp,nconnect=8,timeo=600,retrans=2,_netdev,nofail,x-systemd.automount,x-systemd.idle-timeout=60"

9.5. Playbook D: Permission Denied (`EACCES` / `EPERM`) on Writing Backups

Playbook: Fix UID/GID Squash & Directory OwnershipNFS Server
# 1. Verify /etc/exports contains no_root_squash
$ cat /etc/exports | grep pve-storage
# 2. Reset filesystem permissions and reload export table
$ chmod 777 /nfs-pool/pve-storage && exportfs -arv
